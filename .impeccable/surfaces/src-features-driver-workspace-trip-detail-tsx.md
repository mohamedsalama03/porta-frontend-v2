# Driver Trip Actions

Mode: Operate. This brief applies to the authorized trip-action extension of `/driver/trips/[id]`. It preserves the incumbent Driver identity and explicitly supersedes the old claim that trip actions are unavailable or managed only by operations in `.impeccable/surfaces/src-features-driver-workspace-home-tsx.md` and `docs/DRIVER-INTERFACE-DESIGN.md`, for this scope only. Root product/design files, their sidecar, earlier briefs and historical reports remain unchanged.

Status: Built presentation documented on 2026-09-14 (Africa/Tripoli). The final independent visual review inspected all 53 current PNGs and returned `ship`, with no material presentation fixes. This is a scoped visual disposition; live acceptance, engineering gates, performance and deployment are separate.

Audience and task: Authenticated Arabic-speaking drivers reviewing an assigned trip on a phone, confirming an operation returned by the service, and reviewing the authoritative result. Identity, scope, action availability and lifecycle rules remain service-owned.

THESIS: Read the trip's route and current status, choose a returned allowed operation, review its context in an inline confirmation, then act deliberately and wait for authoritative feedback.

OWN-WORLD: Extend the established Cairo/Arabic RTL Driver workspace with restrained teal actions, neutral light/dark surfaces, thin borders and the existing small radii. No new visual identity, comp, concept round, raster asset or decorative motion is required. Preserve dedicated Driver navigation and existing safe content boundaries.

STORY: Open assigned trip detail. Read route, departure and status before the action area and shipment list. Display only actions contained in the generated `meta.allowed_actions`; `START`, `CONFIRM_ARRIVAL`, `COMPLETE` is presentation order only. Select an action, review repeated route/departure/current status and its Arabic explanation, then confirm or return. Display pending, authoritative success, uncertainty, conflict review or safe unavailable feedback as supplied by the state layer.

FIRST VIEWPORT: Keep return navigation, the trip page heading/time context and the bordered trip detail before action choices. The existing shell caps content at 1040px. Phones use 20px main inline padding and safe-area-aware fixed bottom navigation, with `92px + env(safe-area-inset-bottom)` reserved beneath content. At 768px navigation becomes a static top row and main padding becomes 32px. The trip's shipment section follows action/read feedback; this extension does not reorganize the shell or create a dashboard.

FORM: Full-width action choices form a vertical stack with 12px gaps. Inline confirmation uses the existing 12px surface radius, thin border, neutral surface and 24px by 20px padding. Controls use 8px radii and at least 48px height; confirm/return stack on phones and share a row at 768px and above. Cairo page titles are 26px, trip route headings 22px and confirmation/result headings 20px. Body copy inherits 14px/1.75; the route inside confirmation is bold body text. Request references are isolated LTR, and departure uses the shared Africa/Tripoli formatter.

Memorable interaction: Selecting an action reveals contextual confirmation in the document flow. Focus moves to its heading; return or Escape cancels an unsubmitted selection and restores focus to the initiating choice. Pending blocks duplicates and names the operation in progress. A validated authoritative response produces a named, announced success with a focused heading; further action stays blocked until a fresh trip read has checked current metadata. This is an inline section, not a dialog or optimistic completion flow.

Contract and privacy boundary: Availability is exclusively generated `meta.allowed_actions`, never trip/shipment status, counts, roles or a frontend lifecycle table. The display module owns labels and explanatory copy only. All operations use the centralized HTTP client and approved frontend-local contract; completion conditions and shipment updates remain backend rules. Preserve existing authenticated Driver access and removal of denied private resources. Do not add admin presentation, enrichment, contact persistence, telemetry, GPS/maps, proof of delivery, scanning, PWA behavior or offline mutations.

State contract: Replacing a detail snapshot invalidates an unsubmitted confirmation. Uncertain retries retain their logical request in Driver memory across navigation; session cleanup removes it. A 409 clears the attempt and refreshes authoritative state for review. A 422 clears the rejected attempt/confirmation and requires a new deliberate confirmation. Retry-After is a visible countdown whose expiry never submits. Review failures leave actions blocked behind a deliberate read-retry control. A 401/403/404 invokes the existing access/resource revocation path. The empty metadata state says `لا توجد إجراءات متاحة حاليًا.` and keeps useful reads/navigation. No optimistic success, automatic write retry, silent overwrite, or persistent private/offline queue.

FINISH: `reports/driver-trip-actions/visual/results.json` reports PASS for 50 measured states: ten states at each of light 390, 430, 768 and 1440px and dark 390px. The ten are no-action, start-available, start-pending, start-success, stale-409, arrival-available, complete-available, completed, unavailable-404 and START confirmation. Three extra scrolled confirmation viewports at light 390/430 and dark 390 yield 53 PNGs. `FINISH-REVIEW.md` inspected every image and returned `ship`. The matrix reports zero axe violations, overflow or undersized targets; primary controls meet 48px. RTL/theme/reduced-motion/no-running-animation/no-admin-chrome/no-raw-error/no-private-persistence checks pass. Each scrolled confirmation viewport reports zero buttons below navigation. The single `reports/driver-trip-actions/design-detector.json` result is `[]`.

Evidence limits: (1) The matrix uses synthetic intercepted Chromium session/read/action responses, with unexpected API/external requests blocked; it proves no live write, shipment cascade, live account or production integration. (2) Phone-sized viewports are not physical-device or software-keyboard validation. (3) Automated axe/source checks are not manual screen-reader validation or complete conformance. (4) Still images do not prove keyboard/focus/Escape, announcements, retries or concurrency; separate browser/action tests own those interactions. Arrival/completion availability is captured, while their confirmation/success behavior is source/test scope. (5) Field performance/SLA, final engineering acceptance and deployment are reported elsewhere. Full-page phone images retain navigation at the initial fold; the three scrolled viewports separately establish confirmation-control visibility. The finish reviewer did not operate a live browser/service or physical device.

Unresolved presentation decisions: None within the reviewed extension. Preserve evidence boundaries and current metadata authority when extending the surface. The complete scoped record is `docs/DRIVER-TRIP-ACTIONS-DESIGN.md`; no historical action prohibition or fixture-specific state sequence is canonized into the new system.
